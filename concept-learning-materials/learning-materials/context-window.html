Concept Learning Card

LLM 的上下文窗口（Context Window）

一次推理里，模型"看得见"的 token 总预算——输入（系统提示 + 对话历史 + 工具定义 + 检索结果）与模型要生成的输出，共享同一块有限空间 [来源 1][来源 5]。

生成日期：2026-09-10 · 学习视角：AI Agent 工程入门 · 资料来源均为公开可核查链接

01学习目标

  • 理解"上下文窗口"到底装了什么——它不只是用户输入，还包含系统指令、工具定义、检索资料和模型自己的输出，全部竞争同一份 token 预算 [来源 5]。
  • 能区分模型上下文窗口（model context window）与有效上下文（effective context），并解释为什么"窗口很大"不等于"塞满也能用好"（context rot / Lost in the Middle）[来源 1][来源 2]。
  • 能算一笔账：按输入 / 输出 / 工具 / 记忆的预算拆窗口，判断某条请求会不会超窗，以及用什么手段（压缩、外置、检索、缓存）把它塞回窗口 [来源 1]。

02核心问题

  • "128K / 200K / 1M tokens"说的到底是输入上限还是输入 + 输出的总和？两者的口径有什么差别？
  • 窗口是有限的，但模型的注意力质量是不是随窗口的增大而"摊薄"？什么时候窗口会"名不副实"（effective < model）？
  • 当一次请求装不下窗口时，工程上有哪些具体手段？各自适合什么场景？

03个人解释

我的理解：

我一开始把"上下文窗口"理解成"模型的记忆力上限"，学完才发现它更像一张物理上就装得有限的 A4 纸——不是模型愿意记多少，而是这张纸只能容纳这么多个字。而且这张纸上不只写"我发给它的问题"，还写满了系统指令（人设、规则）、工具说明书（函数 schema）、检索到的资料、之前每一轮对话，最后还要留空给模型自己写的回答。一旦写满，最老的对话就得被"裁掉"。

让我印象最深的是两点。第一，窗口大 ≠ 用得好：就算纸有 1M 字，你把 90 万字塞满后，模型找关键信息的能力也会明显下降（context rot）；而且它尤其容易忽略"中间"那段（Lost in the Middle）——关键信息放在开头和结尾最保险 [来源 1][来源 2]。第二，"模型窗口"和"有效窗口"不是一回事：一个标称 128K 的模型，真正能稳定记住并取用信息的容量常常小得多。所以工程上不能只盯厂商标的那个数字，得按"我最多能可靠用到多少"来做预算 [来源 1]。

站在大二这个节点回头看，我现在再用 ChatGPT 时，会先想"这一段话会不会把之前重要的东西挤出去"——长对话里它"忘了"前面定的要求，现在我知道那通常是早期内容被挤出窗口，不是它故意敷衍。以后我写提示时会有意识地：把最重要的目标放在开头、结尾前再重申一次、无关的闲聊删掉，本质上就是在做最朴素的"上下文窗口管理"。——杨国美

04核心机制 / 组成

① 它装的是什么：一次推理里共享同一份 token 预算的组件。所有输入组件 + 模型要生成的输出，一起计入窗口 [来源 5]：

  • 系统指令（system prompt）：身份、规则、输出格式约定。
  • 工具 / 函数定义：每个可调用的工具的 schema 都占 token，工具越多占用越大。
  • 对话 / 任务历史：之前每一轮（用户 + 模型）都在窗口里。
  • 外部资料：检索（RAG）回来的段落、粘贴的文档、工具调用返回的 JSON。
  • 模型输出：本次要生成的回答本身也占预算，且输出上限通常远小于窗口——比如 GPT-4o mini 是 128K 窗口、最多 16K 输出 [来源 3]。

② 为什么窗口是有限的：架构根因。Transformer 中每个 token 都要与上下文里其它 token 做注意力，计算量随序列长度呈 平方级（n²）增长 [来源 4]——这就是为什么"无限制窗口"不免费，越大越贵、越慢，注意力也被越摊薄。

③ 两个层次的"窗口"（关键区分）：

  • 模型上下文窗口（model context window）：模型架构能装下的硬上限（如 128K / 200K / 1M）。这是厂商标的那个数字 [来源 5]。
  • 有效上下文（effective context）：模型能可靠利用的那部分，通常 < 模型窗口。窗口越大，"装得下"不等于"用得上"——这是 context rot 的直接后果 [来源 1]。

④ 两个"装不进用不好"的失败现象：

  • Context Rot（上下文腐化）：随窗口内 token 增多，模型准确召回其中信息的能力下降——所有模型都有，只是程度不同 [来源 1]。
  • Lost in the Middle（中间迷失）：模型对"开头 / 结尾"的信息关注度高，对"中段"容易失准；即使标称支持长上下文也如此。对策：关键信息放首尾 [来源 2]。

⑤ 超窗 / 装不进时的工程手段（对应"上下文工程"）[来源 1]：

手段做什么适合场景
压缩（Reduce）对历史 / 资料做摘要，只留关键结论多轮长对话、旧轮次信息可概括
外置（Offload）大块资料落盘到文件 / 记忆，只把引用进窗口大文档、可回溯、反复引用
检索（Retrieve）按需 RAG，只把相关片段进窗口语料海量 / 持续增长 / 需精确溯源
隔离（Isolate）不同子任务用独立上下文，避免互相污染多步 Agent、并行子任务
缓存（Cache）对稳定内容做提示缓存，省重复消耗重复用的系统提示 / 固定参考资料

一次推理里的 token 预算分配（示意）

[系统指令] + [工具定义] + [历史对话] + [检索资料] → 输入侧（占大部分） [本次要生成的回答] → 输出侧（上限常远小于窗口，如 16K） 两者之和 ≤ 模型上下文窗口（如 128K），且"有效可用"往往更小

06应用场景（具体例子）

场景：一个客服 Agent，用 GPT-4o mini（窗口 128K），要处理一段平均 80 轮的长对话，每轮约 300 token（用户 + 机器人），外加 4K 的系统人设、6 个工具定义共约 2K，还要留给回答 16K 输出预算。

  • 算账：固定开销 ≈ 4K(系统) + 2K(工具) + 16K(预留输出) = 22K。剩下给对话 ≈ 128K − 22K = 106K，约能装 106K / 300 ≈ 350 轮——但真实里一旦要检索订单、拉日志，token 暴涨，实际可用轮数远低于此。
  • 窗口快满时的做法：① 对早期 200 轮做摘要压缩，保留"用户要退货、已查订单号 X"这类关键结论（Reduce）；② 把完整订单 / 日志外置到文件系统，只对模型说"订单详情已存 /orders/123"，需要时再取（Offload）；③ 把"当前最该解决的核心诉求"重写到对话末尾，避免它沉到中段被忽略（对抗 Lost in the Middle）[来源 1][来源 2]。
  • 结果：在不丢关键事实的前提下把上下文压回窗口内，回答仍然"记得用户要退货"，而不是重复问"请问您想做什么"。

07易混淆 / 使用边界

① "模型窗口" ≠ "有效上下文"。1M 的标称窗口不意味着模型能稳定记住并取用 1M。做容量规划要看有效容量（通常更小），别按标称数字把关键信息排在很远的位置 [来源 1]。

② "窗口" ≠ "记忆"。上下文窗口是单次推理的临时视野，推理结束就没了；它不是跨会话的长期记忆。长期记忆要靠外置（文件 / 向量库 / 记忆模块）。

③ "窗口" ≠ "输入上限"。很多资料（如 OpenAI 给 GPT-4o 的 128K）指的口径是输入 + 输出的总和。做请求前务必确认：你看到的是"输入上限"还是"总预算"，否则一算会超窗 [来源 3][来源 5]。

④ "窗口越大越好" 是误区。窗口放大带来更高的成本（按 token 计费）与延迟（n² 注意力），且不一定提升质量（context rot / Lost in the Middle）。够用即可，超出部分用压缩 / 外置 / 检索解决 [来源 1][来源 2][来源 4]。

⑤ 长上下文 ≠ RAG 的替代品，而是互补。文档少且稳定可整段放窗口；海量 / 持续增长 / 需精确溯源必须靠 RAG。窗口再大也装不下"整个互联网 + 所有历史"。

08自测问题

覆盖四个维度：概念辨析 / 核心机制 / 应用 / 风险边界。建议先盖住答案自测，再点开核对。

Q1（简答·机制）：一次推理里，除"用户输入"外，通常还有哪些东西一起占用上下文窗口？
答：系统指令（人设 / 规则）、工具 / 函数定义（schema）、对话与任务历史、检索 / 工具返回的外部资料，以及模型本次要生成的输出——全部计入同一份 token 预算 [来源 5]。
Q2（简答·概念辨析）："模型上下文窗口"和"有效上下文"分别指什么？为什么说两者不是一回事？
答：模型上下文窗口是架构能装下的硬上限（如 128K / 1M）；有效上下文是模型能可靠取用的那部分，通常更小。标称越大，越容易"装得下但用不上"，因为长上下文会 context rot、中间信息易被忽略 [来源 1][来源 2]。
Q3（简答·风险边界）：什么是 context rot？它说明了"把窗口开到最大"能根治所有长对话问题吗？
答：context rot 指窗口内 token 一多，模型准确召回其中信息的能力下降，所有模型都有、程度不同。开大窗口不能根治——只会推迟、不消除问题，正确做法是上下文工程（压缩 / 外置 / 检索 / 隔离 / 缓存）[来源 1]。
Q4（简答·机制）：Lost in the Middle 观察到了什么现象？由此得到的"排版"建议是什么？
答：模型对开头与结尾的信息利用最好，对中段信息利用率明显下降，即使长上下文模型也如此。建议：把最关键的目标 / 结论放在首尾，中间放可容错的内容 [来源 2]。
Q5（选择·概念辨析）：下列关于"上下文窗口"的说法，正确的是？
答：正确答案 B。
A. "上下文窗口就是用户的输入上限" —— 错，输入 + 输出（以及系统 / 工具 / 历史）共享同一预算 [来源 5]。
B. "上下文窗口是模型一次推理能纳入的最大 token 量，输入和输出共享它" —— 对 [来源 5]。
C. "窗口越大，模型一定能记住并使用全部信息" —— 错，存在有效上下文 < 模型窗口、context rot、Lost in the Middle [来源 1][来源 2]。
D. "上下文窗口是跨会话的长期记忆" —— 错，它是单次推理的临时视野，结束即清零。
Q6（选择·风险边界）：一个 Agent 多轮执行后回答越来越偏题、开始"忘记最初目标"，最可能的主因和对症手段是？
答：正确答案 B。
A. "模型权重损坏，需更换模型" —— 无关，是窗口管理问题。
B. "早期目标被挤出 / 沉到中段，做摘要压缩 + 把核心目标重写到末尾" —— 对，对应 Reduce 与对抗 Lost in the Middle [来源 1][来源 2]。
C. "把 max_tokens 改大就行" —— 错，那扩的是输出侧，不能救输入侧的目标丢失。
D. "把窗口换成更大的模型就一劳永逸" —— 错，context rot 依然存在，正确做法是上下文工程 [来源 1]。
Q7（应用·设计）：你要用 Claude（窗口 200K）让模型通读一份 600 页产品手册并回答"退款政策"相关问题。直接整本粘贴显然不现实，请给出两种以上工程手段并说明理由。
答题要点：
① 检索（RAG）——把手册分块索引，按问题只把"退款"相关段落拉进窗口，避免塞 600 页（手册远超有效可用，context rot 会拉低召回）。
② 外置（Offload）——手册落盘到文件 / 向量库，窗口里只放"已存 index 路径"，模型按需引用。
③ 排版——把用户当前问题与"请严格按手册作答"放在上下文首尾，避开中段盲区。
④ 若后续还要反复问同一手册，用缓存固定住公共部分，省 token 与延迟。
Q8（应用·评价）：同事说："我把模型从 128K 升到 1M，以后就不用做检索了，所有资料一股脑塞进去最省心。"请结合本资料指出这个说法的问题。
答题要点：
① 窗口大 ≠ 用得好——有效上下文通常远小于标称值，塞满后 context rot 会让召回下降 [来源 1]。
② 成本 / 延迟：按 token 计费 + n² 注意力，1M 窗口单次请求成本和延迟都显著上升 [来源 4][来源 5]。
③ 信息组织：全量塞入还会触发 Lost in the Middle，关键结论若在中段易被忽略 [来源 2]。
④ 正确策略是按量选型：资料少且稳定就放窗口；海量 / 增长 / 需精确溯源就 RAG；用压缩 + 外置 + 检索 + 缓存组合做"上下文工程"，而不是靠堆窗口。
